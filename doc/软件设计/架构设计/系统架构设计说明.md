## 1. 架构选型分析

### 1.1 关键质量属性识别

根据《需求规格说明书》中的功能需求与非功能需求，提炼出与体系结构设计最相关的两个质量属性：

| 质量属性 | 来源需求 | 核心指标 | 对架构的影响 |
|---------|---------|---------|------------|
| **可扩展性** | NFR-06 AFD 协议动态扩展；FR-01 多模板支持 | 新增高校论文模板仅需添加 JSON 配置文件，无需修改核心代码或重新编译 | 要求样式定义与核心渲染逻辑解耦，支持插件式模板加载 |
| **性能** | NFR-01 打字延迟 < 30ms；NFR-02 冷启动 < 5s、推理 >= 2 tokens/s | 编辑器实时响应、AI 推理延迟可接受 | 要求减少不必要的中间层开销，UI 线程不被阻塞，AI 推理异步执行 |

### 1.2 备选架构模式对比

针对桌面客户端应用场景，选取两种主流体系结构模式进行对比分析：

#### 方案 A：严格分层架构（Strict Layered Architecture）

```
┌─────────────────────────┐
│    表示层 (Presentation)  │  ← Avalonia UI Views
├─────────────────────────┤
│    业务逻辑层 (Business)   │  ← 所有业务服务
├─────────────────────────┤
│    数据访问层 (Data)       │  ← 文件 I/O、SQLite、Pandoc CLI
└─────────────────────────┘
```

- **层间规则**：每层仅能调用其直接下层，不可跨层调用
- **优点**：层次清晰、职责明确、便于团队分工、上层对下层无感知
- **缺点**：
  - 严格的逐层调用在实时编辑场景中引入不必要的间接开销（与 NFR-01 <30ms 打字延迟冲突）
  - 跨层数据传递需要多次 DTO 转换，增加内存分配和 GC 压力
  - 对 Avalonia UI 的数据绑定机制（直接绑定到 ViewModel）不友好

#### 方案 B：MVVM + 分层混合架构（MVVM + Layered Hybrid）

```
┌──────────────────────────────────────────┐
│              表示层 (UI Layer)             │
│  ┌──────────┐  ┌──────────────────────┐  │
│  │  Views   │  │     ViewModels       │  │
│  │ (XAML)   │◄─┤  (数据绑定 / 命令)    │  │
│  └──────────┘  └──────────┬───────────┘  │
├────────────────────────────┼──────────────┤
│              服务层 (Service Layer)       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │ 文档编辑  │ │ 文档转换  │ │ AI 辅助  │  │
│  │ 服务     │ │ 服务     │ │ 服务     │  │
│  └──────────┘ └──────────┘ └──────────┘  │
├───────────────────────────────────────────┤
│           基础设施层 (Infrastructure)       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │ 文件管理  │ │ Pandoc   │ │LLamaSharp│  │
│  │          │ │ CLI 适配 │ │ 模型管理 │  │
│  └──────────┘ └──────────┘ └──────────┘  │
└───────────────────────────────────────────┘
```

- **表示层**：采用 MVVM 模式，Views 通过数据绑定直接与 ViewModels 交互，ViewModels 通过依赖注入调用服务层接口
- **服务层**：按业务领域垂直划分为独立服务模块，模块间通过接口通信，避免环形依赖
- **基础设施层**：封装外部依赖（Pandoc CLI、LLamaSharp、文件系统），对服务层暴露抽象接口
- **优点**：
  - ViewModel 与 View 的数据绑定消除样板代码，满足编辑器的实时响应要求
  - 服务层按领域拆分，AFD 模板加载作为独立插件模块，天然支持可扩展性
  - 基础设施层抽象化外部依赖，便于单元测试和跨平台适配
- **缺点**：
  - 相比严格分层，需要更细致的依赖管理
  - ViewModel 的职责边界需要明确约束，避免逻辑泄漏到 View

### 1.3 对比总结

| 维度 | 严格分层架构 | MVVM + 分层混合架构 |
|------|------------|-------------------|
| 打字延迟 (<30ms) | 多次层间 DTO 转换，延迟较高 | 数据绑定直连 ViewModel，延迟低 |
| AFD 模板扩展 | 需修改业务层代码 | 插件式加载，符合开闭原则 |
| 与 Avalonia UI 契合度 | 一般，需额外适配 | 原生支持 MVVM 模式 |
| 模块独立测试 | 层间耦合，需集成测试 | 服务接口可 Mock，单元测试友好 |
| 团队学习成本 | 较低（经典模式） | 中等（需理解 MVVM + DI） |
| 冷启动时间 | 相当 | 相当 |

### 1.4 选择结论

**选择方案 B：MVVM + 分层混合架构**。

选择理由：

1. **框架原生契合**：Avalonia UI 基于 XAML 的数据绑定机制深度依赖 MVVM 模式，采用此架构可最小化框架对抗成本，直接利用 Avalonia 的 Binding、Command、Behavior 等机制实现高性能 UI 更新。

2. **性能保障**：ViewModel 直接绑定 View，用户在 Markdown 编辑器中的每次击键仅触发属性变更通知（`INotifyPropertyChanged`），无需穿越多层抽象，保障 NFR-01 要求的 <30ms 打字延迟。

3. **可扩展性支撑**：服务层的模块化设计使得 AFD 协议模板可以作为独立插件动态加载——新增模板只需将新的 JSON 文件放入指定目录，由 `AFDPluginManager` 自动发现并注册，无需重新编译系统核心代码，满足 NFR-06 的可扩展性要求。

4. **离线优先保障**：所有服务层模块在进程内运行，基础设施层仅调用本地资源（文件系统、Pandoc CLI、GGUF 模型），天然满足 NFR-03 的 100% 离线可用性要求。

## 3. 子系统 / 模块划分及职责说明

### 3.1 表示层 — WeaveDoc.UI

| 项 | 说明 |
|----|------|
| **职责** | 用户界面渲染、交互事件处理、数据绑定展示 |
| **核心技术** | Avalonia UI XAML、ReactiveUI、Data Binding |
| **主要组件** | MainWindow、EditorView（左右分屏布局）、PDFViewer、ExportDialog、ChatPanel、SnapshotTimeline |
| **主要 ViewModel** | MainViewModel、EditorViewModel、PDFViewerViewModel、ExportViewModel、ChatViewModel、SnapshotViewModel |
| **对外接口** | 通过依赖注入（DI）消费服务层接口；不直接访问基础设施层 |

**设计约束**：
- View 层仅包含 XAML 布局和样式，不含业务逻辑
- ViewModel 不持有 View 引用，通过 `INotifyPropertyChanged` 驱动 UI 更新
- 所有耗时操作（AI 推理、文档转换）通过 `async/await` 异步调用，不阻塞 UI 线程

### 3.2 文档编辑子系统 — WeaveDoc.Editing

| 项 | 说明 |
|----|------|
| **职责** | Markdown 文本编辑、PDF 渲染与浏览、双屏滚动同步、深层链接锚点生成 |
| **服务接口** | `IEditorService`、`IPDFViewerService`、`ISyncEngine`、`IAnchorService` |
| **依赖** | 基础设施层 `IFileService`（文件读写） |
| **对外暴露** | 编辑状态变更事件、光标位置、锚点数据 |

**核心类设计**：

| 类 | 职责 |
|----|------|
| `MarkdownEditor` | 管理 MD 文档的文本缓冲区、语法高亮、撤销/重做栈 |
| `PDFRenderEngine` | 基于 Avalonia 渲染 PDF 页面，处理缩放与翻页 |
| `SyncEngine` | 计算 MD 与 PDF 卷动位置的映射关系，实现双向同步联动 |
| `AnchorService` | 生成 PDF → MD 的深层链接锚点，管理锚点跳转 |

### 3.3 文档转换子系统 — WeaveDoc.Conversion

| 项 | 说明 |
|----|------|
| **职责** | AFD JSON 模板解析与校验、Markdown → IR 中间表示转换、Pandoc 管线编排、GB/T 7714 引文重排、高保真文档导出 |
| **服务接口** | `IAFDParser`、`IIRGenerator`、`IPandocPipeline`、`ICitationFormatter`、`IExportService` |
| **依赖** | 基础设施层 `IPandocAdapter`、`IFileService`；文献管理子系统 `ICitationIndex` |
| **对外暴露** | 导出结果、格式校验错误列表 |

**核心类设计**：

| 类 | 职责 |
|----|------|
| `AFDParser` | 加载并校验 AFD JSON Schema，将样式定义反序列化为 `AFDTemplate` 实体 |
| `IRGenerator` | 将 Markdown AST 转换为系统内部 `DocumentIR` 中间表示 |
| `PandocPipeline` | 组装 Pandoc CLI 参数、执行转换、捕获输出与错误 |
| `CitationFormatter` | 按 GB/T 7714-2015 规范对正文引文重新编号，同步更新参考文献列表 |
| `ExportService` | 编排完整导出流程：解析模板 → 生成 IR → 引文重排 → 调用 Pandoc → 输出文件 |
| `AFDPluginManager` | 扫描模板目录，动态发现并注册新的 AFD JSON 模板文件 |

### 3.4 AI 辅助子系统 — WeaveDoc.AI

| 项 | 说明 |
|----|------|
| **职责** | PDF 文档切片与向量化、本地向量存储与相似度检索、RAG Prompt 组装与 LLM 推理、PDF 公式区域 OCR 识别与 LaTeX 转换 |
| **服务接口** | `IEmbeddingService`、`IVectorStore`、`IRAGEngine`、`ILLMInferenceService`、`IOCRService` |
| **依赖** | 基础设施层 `ILLamaAdapter`、`IFileService` |
| **对外暴露** | 流式 RAG 回答、LaTeX 公式字符串 |

**核心类设计**：

| 类 | 职责 |
|----|------|
| `EmbeddingService` | 对 PDF 文本切片调用本地 Embedding 模型生成向量 |
| `VectorStore` | 使用本地嵌入式向量数据库存储和检索文档向量（支持余弦相似度 / 欧氏距离） |
| `RAGEngine` | 接收用户问题 → 检索相关上下文 → 组装 System Prompt → 调用 LLM → 流式返回 |
| `LLMInferenceService` | 封装 LLamaSharp，管理模型加载/卸载、推理参数配置、Token 流式输出 |
| `OCRService` | 对用户框选的 PDF 区域调用本地视觉模型进行公式识别，输出 LaTeX 代码 |

### 3.5 文献管理子系统 — WeaveDoc.Literature

| 项 | 说明 |
|----|------|
| **职责** | BibTeX 文献数据库解析与索引、Zotero Better BibTeX 实时同步、文献条目与本地 PDF 文件匹配、文稿版本增量快照与回滚 |
| **服务接口** | `IBibTeXParser`、`IZoteroSyncService`、`ICitationIndex`、`ISnapshotService` |
| **依赖** | 基础设施层 `IFileService`、`IConfigurationService` |
| **对外暴露** | 文献元数据集合、引文索引映射表、快照时间轴数据 |

**核心类设计**：

| 类 | 职责 |
|----|------|
| `BibTeXParser` | 解析 .bib 文件，提取作者、标题、年份、DOI 等字段，构建 `BibEntry` 实体集合 |
| `ZoteroSyncService` | 监控 Zotero Better BibTeX 数据库文件变更，自动增量同步文献条目 |
| `CitationIndex` | 维护正文引用标记 `[key]` 与文献条目的映射，支持增删改后自动重排 |
| `SnapshotService` | 每 5 分钟自动触发增量快照（记录文件 diff），管理快照生命周期 |
| `SnapshotStore` | 快照文件的持久化存储与索引，支持时间轴查询与版本恢复 |

### 3.6 基础设施层 — WeaveDoc.Infrastructure

| 项 | 说明 |
|----|------|
| **职责** | 封装所有外部依赖和系统级服务，为服务层提供平台无关的抽象接口 |
| **主要组件** | `FileService`、`PandocAdapter`、`LLamaAdapter`、`ConfigurationService`、`AuditLogger`、`SQLiteDatabase` |

**PandocAdapter 设计要点**：
- 通过 `System.Diagnostics.Process` 启动 Pandoc CLI 子进程
- 支持 `--from markdown --to docx/pdf --reference-doc=<AFD模板>` 等参数组装
- 进程隔离确保 Pandoc 崩溃不影响主进程

**LLamaAdapter 设计要点**：
- 封装 LLamaSharp 的 `LLamaWeights` 和 `LLamaContext` 生命周期
- 支持模型热加载/卸载以控制内存占用（峰值 ≤ 80% 物理内存）
- 提供 `IAsyncEnumerable<string>` 流式输出接口

## 5. 关键技术与设计决策

### 5.1 核心技术栈

| 技术领域 | 选型 | 版本 | 选型依据 |
|---------|------|------|---------|
| 运行时 | .NET | 10.0 | 项目约束；.NET 10 提供更好的 NativeAOT 支持和性能优化 |
| UI 框架 | Avalonia UI | 11.x | 项目约束；跨平台（Win/Linux）一致性渲染，XAML 数据绑定原生支持 MVVM |
| AI 推理 | LLamaSharp | 0.x (.NET 10 兼容) | 项目约束；支持 GGUF 格式量化模型，纯本地进程内推理 |
| 文档转换 | Pandoc | 3.x | 项目约束；业界标准文档转换引擎，支持 Markdown → Word/PDF |
| 模板响应式 | ReactiveUI | 20.x | 与 Avalonia 深度集成，提供响应式数据流和命令绑定 |
| 依赖注入 | Microsoft.Extensions.DI | 10.0 | .NET 官方 DI 容器，轻量且功能完备 |
| 向量数据库 | SQLite + 向量扩展 | - | 本地嵌入式方案，零配置零网络依赖，满足离线约束 |
| 配置管理 | .NET Configuration | 10.0 | 支持 JSON 文件、环境变量等多种提供程序 |
| 日志 | Serilog | - | 结构化日志，支持文件持久化满足审计追踪需求 |

### 5.2 重要设计决策

#### 决策 1：中间表示层（IR）作为模块间统一数据格式

- **决策**：定义 `DocumentIR` 作为 Markdown 编辑器、AFD 解析器和 Pandoc 管线之间的唯一数据交换格式
- **依据**：需求要求 AFD 样式与核心代码解耦，IR 作为内容与样式的"契约层"，使得样式模板变更不影响编辑器，编辑器 AST 变更不影响导出管线
- **代价**：需维护 IR ↔ Markdown AST ↔ Pandoc AST 的双向映射

#### 决策 2：Pandoc 通过子进程调用而非内嵌

- **决策**：Pandoc 作为独立 CLI 进程调用，通过 `System.Diagnostics.Process` 管理生命周期
- **依据**：
  - Pandoc 为 Haskell 编写，无 .NET 原生绑定，嵌入成本极高
  - 子进程隔离确保 Pandoc 崩溃不影响主编辑进程
  - 更易于跟随 Pandoc 版本升级，无需重新编译 WeaveDoc
- **代价**：进程启动开销约 100-200ms，但对于导出操作（用户主动触发）可接受

#### 决策 3：向量数据库选用 SQLite 而非专用向量数据库

- **决策**：基于 SQLite 存储文档向量，利用 BLOB 字段存储 float 数组
- **依据**：
  - 部分专用向量数据库（如 Milvus）需要额外服务进程，破坏"本地优先"约束
  - MVP 阶段的文献规模有限（数十篇 PDF），SQLite 的线性扫描 + 缓存策略足够应对
  - 零部署依赖，SQLite 随 .NET 运行时自带
- **代价**：文档量级增长后检索性能可能下降，后续可迁移至 Qdrant 等嵌入式向量数据库

#### 决策 4：增量快照采用内容寻址存储

- **决策**：每次快照仅存储文件变更的 diff（基于文本行级比较），而非完整副本
- **依据**：学术文档以纯文本 Markdown 为主，行级 diff 压缩率高，减少磁盘占用
- **代价**：恢复时需从基线和所有增量 diff 重建，计算复杂度 O(快照次数)

#### 决策 5：ReactiveUI 响应式编程

- **决策**：在 ViewModel 层引入 ReactiveUI，使用 `WhenAnyValue`、`ReactiveCommand` 等响应式原语
- **依据**：双屏联动滚动、搜索防抖、引文更新等场景涉及多属性联动，命令式代码复杂且易出错，响应式编程更简洁
- **代价**：团队需学习 ReactiveUI 编程范式

## 6. 技术风险分析

| 风险编号 | 风险描述 | 影响等级 | 发生概率 | 应对措施 |
|---------|---------|:-------:|:------:|---------|
| RSK-01 | **本地 LLM 推理性能不达标**：7B 参数量化模型在 16GB 设备上推理速度 < 2 tokens/s，不满足 NFR-02 | 高 | 中 | (1) 预选 Phi-4、Qwen2.5 等多款 SLMs 进行基准测试；(2) 提供模型切换选项，允许用户根据硬件选择更小的模型（如 3B/1.5B）；(3) 实现推理超时降级策略 |
| RSK-02 | **Pandoc CLI 版本兼容性问题**：不同操作系统下的 Pandoc 版本行为不一致，导致导出结果差异 | 中 | 中 | (1) 内置已知兼容的 Pandoc 版本哈希校验；(2) 在启动时检测 Pandoc 版本并提示用户；(3) 提供 Pandoc 参数回退链 |
| RSK-03 | **跨平台 UI 渲染不一致**：Avalonia UI 在 Linux 与 Windows 上控件渲染存在细微差异 | 中 | 中 | (1) 避免使用平台特定 API；(2) 在 Windows 10/11 和 Ubuntu 22.04+ 上持续集成自动化截图对比；(3) 使用 Avalonia 的 Fluent Theme 确保主题一致 |
| RSK-04 | **内存占用超限**：同时加载 LLM 模型 + PDF 渲染 + 向量库导致 16GB 内存不足 | 高 | 中 | (1) 实现模型按需加载与卸载策略（LRU 缓存）；(2) PDF 采用分页渲染而非全量加载；(3) 设置内存水位线告警阈值（>80% 时触发模型卸载） |
| RSK-05 | **Zotero API 不兼容**：Zotero v6/v7 的 Better BibTeX 导出格式存在差异 | 低 | 高 | (1) 针对 v6 和 v7 输出格式编写适配器；(2) 建立 BibTeX 解析的容错机制，兼容格式微调 |
| RSK-06 | **AFD Schema 升级导致旧模板失效**：协议迭代后用户已有的自定义模板无法使用 | 低 | 中 | (1) AFD Schema 内置版本号字段；(2) 提供模板迁移工具自动升级旧版 Schema；(3) 保持至少 1 个大版本的向后兼容 |
| RSK-07 | **16 周工期内无法完成所有 Must Have 需求** | 高 | 中 | (1) 严格按 MoSCoW 优先级交付，先完成模块一（文档排版与导出），再推进模块二、三；(2) 每周迭代评审，及时砍掉 scope creep |
